# 胖虫项目一个月专项策划书（老板审阅版）

> 版本：v1.0  
> 建议周期：2026-07-21 至 2026-08-20  
> 团队：4 人  
> 文件性质：立项与执行计划，不代表功能已经完成

## 1. 项目提案

建议批准一个为期一个月的“商业化基础补强专项”，集中解决真实交易前最影响资金、安全和交付的阻断项，并建立可持续的研发与发布流程。

当前项目已具备商品、DIY 配置、购物车、订单、后台和容器化原型，但商业化评估为 48/100。项目目前适合演示，不适合直接接受真实款项。一个月专项的合理目标是达到邀请制测试和正式支付沙箱验收，而不是对外承诺完整商业化上线。

## 2. 项目目标

### 业务目标

- 形成 20–50 个可销售首发 SKU 的可信商品集。
- 打通“选配—服务端计价—下单—支付沙箱—订单状态—退款沙箱”的闭环。
- 让老板和团队能基于同一套数据看进度、风险与上线条件。

### 技术目标

- 封堵客户端篡改 DIY 价格和生产环境测试管理员等 P0 风险。
- 建立 CI 质量门禁、测试环境、TLS、日志监控和备份恢复基线。
- 将订单、支付和定价逻辑逐步从 API 路由迁移到 service/domain 边界。
- 为正式支付、物流、发票、售后和后续扩展保留清晰接口。

### 管理目标

- 四名成员职责无重叠盲区，每项任务都有负责人、产物和验收人。
- 每周有可演示增量，最后三天只用于验收和修复。
- 任何影响上线的风险在 1 个工作日内登记，超过 2 个工作日未解决则升级。

## 3. 本月范围

### 本月必须完成

1. 服务端可信定价、订单金额一致性和库存并发测试。
2. 正式支付渠道的官方沙箱接入、验签、幂等、退款和对账基础。
3. 生产测试数据隔离、密钥校验、依赖升级、登录/支付/上传限流。
4. 前端结算与支付状态体验、失败恢复、协议确认和移动端验收。
5. 首发 SKU 数据、图片/模型授权、价格来源和库存责任人确认。
6. CI、staging、TLS、结构化日志、监控告警、备份与恢复演练。
7. 上线检查清单、客服/退款/物流异常处理手册和 Go/No-Go 汇报。

### 本月明确不承诺

- 2000 个 SKU 全量录入和全部 3D 建模。
- 多商户入驻、交易撮合或平台型电商能力。
- 微信与支付宝双支付渠道同时正式上线。
- 千单级压测、多地域容灾、完整数据中台或推荐系统。
- 在主体、域名、备案、支付商户材料缺失时承诺正式上线日期。

## 7. 衡量指标

以下是本月验收目标，不是当前完成情况：

- P0 安全与交易阻断项关闭率：100%。
- 核心交易自动化用例通过率：100%。
- 订单/支付/购物车相关后端覆盖率：不低于 75%；后端总覆盖率目标不低于 65%。
- 首发 SKU 抽检通过率：100%。
- staging 备份恢复演练：至少 1 次成功并记录耗时。
- 候选版本连续 3 个工作日无阻断级缺陷。
- 关键 5xx、支付失败和备份失败均能触发告警。

## 8. 资源与费用类别

本策划书不虚构金额，立项时需确认以下费用上限：

- 云服务器、托管数据库、对象存储、CDN、域名和证书；
- 正式支付商户接入、短信/邮件、物流 API；
- 备案、法律文本与隐私合规咨询；
- 安全扫描或第三方渗透测试；
- 商品摄影、3D 资产、图片授权和数据录入。

## 9. 主要风险

- 主体、ICP备案、域名或支付商户材料未准备，外部审批进入关键路径。
- 正式支付验签、退款或对账能力复杂，四周内只能完成官方沙箱。
- 商品数量目标过大，稀释交易和质量基线的投入。
- 团队成员兼职或角色能力不匹配，导致计划中的并行工作串行化。
- 现有依赖升级可能引入兼容性回归，需要预留修复窗口。

详细应对见 [风险登记与上线验收门禁](03-risk-and-acceptance.md)。

## 10. 老板需要确认的 6 项决策

1. 首发业务是自营商城，还是允许第三方商户入驻？
2. 一个月后的目标是“邀请制测试”还是必须“公开真实收款”？
3. 首发支付渠道选择支付宝还是微信，只选一个作为本月主线。
4. 首发 SKU 数量是否接受 20–50 个高质量商品，而非追求 2000 个全量？
5. 公司主体、域名、ICP备案、支付商户和开票能力当前处于什么状态？
6. 云资源、法律/安全服务和商品资产的预算上限是多少？

## 11. Go/No-Go 原则

即使四周计划按时结束，只要以下任一条件未满足，仍不允许公开真实收款：服务端可信定价、正式支付验签与幂等、生产测试账号隔离、HTTPS、备份恢复、关键告警、退款路径、首发 SKU 质量和必要主体/备案材料。

建议老板批准本月专项，并把“是否公开上线”作为 2026-08-20 的独立决策，而不是立项时预先承诺。

## 12. 距离商业化部署的时间判断

| 目标 | 从 2026-07-21 起的基准工期 | 一个月后的预期状态 | 成立条件 |
| --- | ---: | --- | --- |
| 受控邀请测试 | 4 周 | 候选版，可做支付沙箱或严格限额邀测 | 四人全职；P0 全关；staging、备份和告警通过验收 |
| 小流量真实付费 MVP | 8–12 周 | 仍需约 4–8 周完成正式渠道、合规和生产验证 | 主体、域名、备案和支付商户材料可并行推进 |
| 外部材料尚未启动时的付费 MVP | 12–16 周 | 工期主要受外部审批影响 | 老板在第 1 周确定责任人并提交材料 |
| 稳定商业运营版本 | 4–6 个月 | 完成灰度、压测、运营与售后闭环后再评估扩量 | 持续投入、真实运营数据和安全复核 |

因此，本月计划的正确承诺是“把项目推进到可验收的邀测候选版”。若四人并非全职，或支付/备案材料未准备，以上工期需要顺延，不能通过减少支付、安全和恢复验收来压缩。
