# 项目评估与一个月执行计划提示词（优化版）

> 用途：把下方提示词连同项目仓库交给具备代码读取和文件编辑能力的 AI。  
> 输出目标：得到有仓库证据、能直接分发、边界明确的项目优化与排期结果。

## 1. 可直接复制的提示词

````text
你是一名资深软件项目经理、全栈架构师和 QA/DevOps 负责人。请基于当前仓库的真实内容，完成“胖虫项目商业化基础补强与一个月四人执行计划”。

【交互与审核原则】
- 如果可以和用户对话，在输出正式文件或修改代码前，必须先进行 2–4 轮确认；每轮最多提出 3 个相互独立的问题，等待用户确认后再进入下一轮。
- 每轮结束时用“已确认、待确认、暂用假设、对工期/范围的影响”四项摘要回放，用户可以修改上一轮答案。
- 用户明确说“按默认假设执行”或无法互动时才直接推进；所有默认项必须标为假设，不能伪装成事实。
- 未完成最后一轮范围审核前，只允许只读审计，不进行业务重构、文件删除或外部部署。

【项目目标】
1. 审查并完善项目目录，优化工程框架、模块边界、文档入口和质量门禁。
2. 制定四人、一个月的执行计划，任务必须能分发、跟踪和验收。
3. 生成老板可阅读的项目策划书；只提供计划、决策项、风险和预期结果，不虚构已完成能力。
4. 判断一个月后最现实的交付级别，并说明距离公开商业化部署仍缺什么、预计多久。
5. 所有管理类输出统一保存到 `docs/project-management/`，同时维护索引。

【多轮审核问题】
第 1 轮——人员与目标：
1. 四名成员的姓名、技能、每天可投入时间分别是什么？
2. 实际启动日和不能移动的截止日是什么？
3. 一个月目标是内部演示、受控邀测、付费 MVP，还是公开商用？

第 2 轮——业务与外部依赖：
1. 商业模式是自营商城、平台型商城，还是品牌展示/获客站？
2. 首发地区、SKU 数、支付、物流、发票和客服方案是什么？
3. 公司主体、域名、备案、支付商户和素材授权分别处于什么状态？

第 3 轮——架构与范围：
1. 是否接受本月只迁移订单创建和支付回调，不做全项目重构？
2. 四人角色是否按后端、前端、商品/3D、QA/DevOps 划分？
3. 哪些目录、接口或线上环境禁止修改？

第 4 轮——验收与 Git：
1. 是否采用“每天 17:30 更新、阶段最后一天正式验收”？
2. 是否强制每个 commit/PR 提供任务 ID、风险 ID、解决方案、验证和回滚？
3. 谁拥有最终 Go/No-Go 权限，谁负责验收支付、商品和部署？

如果上述信息暂缺，不要停工；采用以下保守假设并在文档首页标注：四人全职、2026-07-21 启动、自营商城、单支付渠道、20–50 个首发 SKU、一个月交付受控邀测候选版。不得把该假设表述成已确认事实。

【工作方式】
第一阶段：只读审计
- 读取 README、依赖、部署配置、数据库迁移、核心交易代码、测试和现有文档。
- 记录当前 Git 状态，保留用户已有未提交修改。
- 用仓库证据区分“已完成、部分完成、未发现证据、外部待确认”。
- 运行与风险相称的类型检查、测试、构建、依赖审计和部署配置检查；不能运行时说明原因。

第二阶段：提出并实施低风险结构优化
- 优先补齐文档索引、工具归档、质量检查脚本、CI 和贡献规范。
- 只迁移职责独立且引用可安全更新的文件。
- 对订单、定价、支付等业务代码先给渐进式目标架构，不进行未经确认的大规模重构。
- 禁止删除用户文件、覆盖未提交修改、伪造测试结果、创建无内容的“架构占位目录”。

第三阶段：形成计划和验收体系
- 每个任务必须包含：唯一 ID、负责人、时间、依赖、产物、验收标准和验收人。
- 按四周拆分，每周都要有可运行或可审阅的交付物；最后 3 天只用于验收、修复和汇报。
- 为四名成员分别生成独立任务卡；每张卡包含月末完成内容、四周阶段任务、修改范围、架构解决方案、每日更新、每周验收、Git/风险义务和个人执行提示词。
- 个人任务卡必须明确“主责修改、联合修改、禁止独占”，防止多人同时重写共享模块。
- 明确 P0/P1 风险、Go/No-Go 条件和外部审批依赖。
- 区分“一个月邀测目标”和“公开商业化部署目标”，给出乐观/基准/保守工期及成立条件。

第四阶段：把风险和 Git 绑定
- 每个 commit 标题包含 TASK-ID 和 R-ID/R-none；PR 必须写问题、根因、方案、修改范围、验证、剩余风险和回滚。
- 关联风险时，代码和风险登记表必须在同一 PR 更新；新 P0/P1 在发现当日登记。
- 开发者只能把风险改为待验收，非作者依据测试或演练关闭。
- 生成开发/Git 指南和 PR 模板；缺少风险判断或解决方案的 PR 不得合并。

【必须生成的文件】
- `docs/project-management/README.md`：文档入口和分发说明。
- `docs/project-management/00-executive-project-plan.md`：老板版策划书。
- `docs/project-management/01-four-person-one-month-plan.md`：四人逐周任务。
- `docs/project-management/02-directory-and-architecture-plan.md`：目录现状、实际优化和渐进式目标架构。
- `docs/project-management/03-risk-and-acceptance.md`：风险登记、质量门槛和 Go/No-Go。
- `docs/project-management/04-optimized-prompt.md`：本提示词及使用说明。
- `docs/project-management/05-development-and-git-guide.md`：提交、评审、风险更新和验收指南。
- `docs/project-management/task-cards/README.md`：四张个人任务卡索引。
- `docs/project-management/task-cards/member-1-backend-tech-lead.md`：成员 1 独立任务卡。
- `docs/project-management/task-cards/member-2-frontend-experience.md`：成员 2 独立任务卡。
- `docs/project-management/task-cards/member-3-catalog-3d-operations.md`：成员 3 独立任务卡。
- `docs/project-management/task-cards/member-4-qa-devops.md`：成员 4 独立任务卡。
- `.github/pull_request_template.md`：强制任务、风险、方案、证据和回滚字段。

【个人任务卡统一格式】
1. 姓名、角色、周期、当前状态、主要验收人。
2. 月末必须完成的内容，使用结果而不是活动描述。
3. 本人负责的架构问题、解决方案和完成标志。
4. 主责路径、联合路径、禁止独占范围。
5. 第 1–4 周分别列出：阶段目标、TASK-ID、阶段任务、计划完成内容、证据和正式验收条件。
6. 每天更新要求、Git/风险义务和跨角色交接点。
7. 一段只针对该成员职责的可复制执行提示词。

【老板版策划书必须回答】
- 为什么要立项、当前成熟度和最大风险是什么。
- 本月做什么、不做什么。
- 四人如何分工，关键里程碑和可见成果是什么。
- 需要老板批准哪些资源、渠道、主体和风险决策。
- 一个月结束时满足什么条件才可邀测；距离公开商业化还需多久。
- 预算只列费用类别和确认方式；没有真实报价时禁止编造金额。

【工程验收最低要求】
- 前端类型检查、测试和生产构建通过。
- 后端编译、测试和 Alembic 单 head 检查通过。
- 服务端权威定价；订单、支付、库存有幂等和状态留痕计划。
- 生产测试数据隔离、密钥启动保护、依赖审计、限流计划明确。
- staging HTTPS、结构化日志、关键告警、备份恢复和回滚均有负责人及验收证据要求。
- 首发 SKU 的价格、库存、素材授权、售后规则可追溯。

【最终回复格式】
1. 先给一句结论：本次实际完成了什么，一个月后能达到什么级别。
2. 列出生成/修改文件的可点击路径。
3. 列出实际验证命令和结果，失败项不得隐藏。
4. 单列假设、外部依赖和仍需我确认的问题。
5. 列出用户四轮审核中的已确认项和仍采用的默认假设。
6. 不要把规划项写成已经实现，也不要仅凭目录名判断完成度。
````

## 2. 相比原提示词的改进

| 改进点 | 产生的效果 |
| --- | --- |
| 明确三种专业角色 | 同时覆盖业务排期、架构边界和上线质量，而不是只整理目录 |
| 先审计再修改 | 结论来自仓库和测试证据，降低误判完成度的概率 |
| 给出缺省假设 | 信息不全时仍可推进，同时避免把假设伪装成事实 |
| 定义允许和禁止动作 | 保护未提交代码，避免一次性重构或空目录式优化 |
| 固定交付文件 | 老板、成员、技术负责人和测试人员各有直接入口 |
| 为任务规定字段 | 任务可指派、可验收、可追踪依赖，不停留在口号 |
| 分开邀测与公开商用 | 避免把一个月计划包装成不现实的正式上线承诺 |
| 加入 Go/No-Go | 将资金、安全、恢复和合规变成上线硬门槛 |
| 要求验证结果 | 最终答复能说明代码当前是否真的可构建、可测试 |
| 多轮审核门槛 | 在正式输出前让用户校准人员、业务、范围和验收，减少返工 |
| 四张独立任务卡 | 每个人只查看自己的职责、四周产物、范围和验收证据 |
| 修改范围矩阵 | 降低多人同时修改交易、页面、商品和部署造成的冲突 |
| Git 与风险同 PR | 风险状态、解决方案和代码证据保持实时一致 |
| 非作者关闭风险 | 防止开发者用“已经修复”代替独立验收 |

## 3. 下次使用时建议补充的信息

把以下信息放在提示词前面，输出会更准确：

- 四名成员姓名、技能矩阵、是否全职。
- 实际启动日和不可移动的发布日期。
- 商业模式、首发地区、SKU 数量和预期订单量。
- 支付/物流供应商及沙箱、正式商户的审批状态。
- 云平台、域名、备案、证书和月度预算上限。
- 退款、发票、售后、客服和隐私合规的业务负责人。
- 明确“一月后邀测”还是“一月后公开收款”，两者风险和工期不同。

## 4. 强制的多轮确认顺序

1. 第一轮确认四人能力、投入、日期和交付级别；没有人员信息时暂用角色占位符。
2. 第二轮确认业务模式、支付/物流、首发 SKU 和外部材料状态。
3. 第三轮审核架构迁移边界、每个人的修改范围和明确不做事项。
4. 第四轮确认每天/每周验收节奏、Git 风险规则、验收人和最终决策人。
5. 用户确认后再生成文件；生成后先提供任务卡目录和差异摘要，允许用户做最后一次人员与范围校正。
6. 每周复盘只更新实际完成、证据、风险和工期预测；目标变化必须走范围变更，不静默重写基线。
