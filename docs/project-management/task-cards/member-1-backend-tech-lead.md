## 负责解决的架构问题

| 架构问题 | 解决方案 | 完成标志 |
| --- | --- | --- |
| 业务逻辑集中在 API 路由 | 建立 `domain`、`services`、`repositories`，先迁移创建订单和支付回调 | 路由不直接决定价格、库存和支付状态 |
| DIY 定价信任客户端 | 建立 Money/Pricing 领域规则，服务端按商品版本重新计价 | 客户端改价测试被拒绝 |
| 支付代码与路由耦合 | 建立 payment adapter 和 payment service，沙箱/生产仅由配置切换 | 验签、幂等、查询、退款接口统一 |
| 状态变更不可追溯 | 增加 payment event、order status history、库存流水 | 重复/乱序事件可审计且不重复入账 |
| 事务与并发边界不清 | repository 显式处理事务、行锁/原子更新和失败回滚 | 并发下单不超卖，失败能恢复 |

## 每日与 Git 要求

1. 每天开始前选择 1–2 个可在当天验证的任务；17:30 更新完成内容、证据和风险。
2. 每个 PR 只迁移一个用例或一个支付边界；迁移与接口破坏不得混在一起。
3. PR 必须填写任务 ID、风险 ID、解决方案、修改范围、验证、migration 和回滚。
4. 涉及 R-01、R-02、R-03、R-04、R-11 时，在同一 PR 更新风险登记表。
5. 自己编写的支付、权限和 migration 不得由自己单独批准。
