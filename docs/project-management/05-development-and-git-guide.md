# 开发、Git 与风险更新指南

> 适用人员：胖虫项目全部开发者  
> 生效日期：2026-07-21  
> 强制规则：代码、任务证据和风险方案必须在同一条 Git 变更链中可追溯

## 1. 开发前先写解决方案

开始编码前，在任务卡、Issue 或 PR 草稿中写清以下内容：

| 必填项 | 要回答的问题 |
| --- | --- |
| 任务 ID | 属于哪一周、哪名成员、哪个验收目标？ |
| 问题和根因 | 当前行为是什么，为什么会发生？ |
| 解决方案 | 修改哪一层，为什么选择该方案？ |
| 修改范围 | 允许修改哪些文件；哪些文件明确不改？ |
| 架构边界 | API/domain/service/repository/integration/UI 中谁负责什么？ |
| 风险 | 关联哪个 R-ID；是否引入资金、数据、权限、发布或合规风险？ |
| 验证 | 需要哪些单测、集成、E2E、构建、截图或演练？ |
| 回滚 | 代码、配置、migration、数据如何恢复？ |

没有明确解决方案时可以创建 Draft PR 讨论，但不得先进行跨模块大改再补说明。

## 2. 分支与提交规范

从最新 `master` 创建短生命周期分支：

```text
feature/<TASK-ID>-<short-name>
fix/<TASK-ID>-<short-name>
docs/<TASK-ID>-<short-name>
```

Commit 标题：

```text
<type>(<scope>): <TASK-ID> [<R-ID>|R-none] <purpose>
```

示例：

```text
fix(order): BE-102 [R-01] calculate diy price on server
test(payment): QA-202 [R-02] cover duplicate callback
docs(catalog): DATA-102 [R-09] define sku completion fields
```

- `R-none` 不是省略风险分析，PR 中必须说明为什么没有风险变化。
- 一个 commit 只表达一个可回滚意图；格式化、迁移和业务行为尽量分开。
- 禁止在提交标题或正文包含密钥、token、用户数据或第三方回调原文。

## 3. 角色修改边界

| 角色 | 主责 | 需要联合评审 |
| --- | --- | --- |
| 成员 1 | 订单、支付、金额、事务、后端分层和 migration | 安全/部署由成员 4；契约由成员 2 |
| 成员 2 | DIY、购物车、结算、支付/售后体验和前端测试 | API 语义由成员 1；商品字段由成员 3 |
| 成员 3 | SKU、价格/库存来源、图片/GLB、物流运营和后台数据 | schema 由成员 1；页面由成员 2；告警由成员 4 |
| 成员 4 | CI、测试环境、Docker/Nginx、监控、备份、发布和风险文档 | 业务规则由成员 1/3；用户影响由成员 2 |

详细路径以[总计划修改范围](01-four-person-one-month-plan.md)和[个人任务卡](task-cards/README.md)为准。超出个人范围前，必须在 PR 说明主责人、必要性、影响和验收人。

## 4. Pull Request 强制内容

仓库的 [PR 模板](../../.github/pull_request_template.md)必须完整填写：

1. 任务 ID、个人任务卡和当前周次。
2. 问题、根因和方案，不接受只有文件列表的说明。
3. 实际修改范围和明确未修改范围。
4. 关联风险、状态变化和风险登记表更新。
5. 验证命令及真实结果，包括警告和失败项。
6. 配置、migration、数据、接口兼容性和回滚方式。
7. 指定非作者验收人。

以下改动至少两人批准：支付、权限、migration、生产配置、备份/恢复、管理员创建和个人信息处理。

`.github/workflows/pr-governance.yml` 会自动检查任务 ID、风险 ID、问题/根因、解决方案、实际/禁止修改范围、验证证据和回滚说明。填写具体 `R-ID` 但未在同一 PR 修改风险登记表时，门禁会失败；`R-none` 仍需人工评审理由是否成立。

## 5. 风险实时更新流程

### 5.1 关联已有风险

在同一 PR 内完成：

1. 更新[实时风险登记表](03-risk-and-acceptance.md)的状态、当前方案、证据/PR 和日期。
2. 在风险变更日志追加开发者、状态变化、方案摘要和验收人。
3. PR 描述说明修改后剩余风险，不得声称风险为零。

### 5.2 发现新风险

发现当日创建下一个 `R-xx`，写明等级、触发条件、负责人、缓解方案、截止时间和关闭证据。P0 立即停止范围扩展并通知项目负责人。

### 5.3 关闭风险

- 开发者只能把状态改为 `待验收`。
- 非作者依据自动化测试、日志、截图、数据核对或演练把它改为 `已关闭`。
- P0 不能通过书面接受绕过；P1/P2 的 `已接受` 必须有老板、期限和缓解方案。

## 6. 每日与每周验收

### 每天 17:30 前

- 更新任务状态和当天实际完成内容。
- 记录 commit/PR、测试和截图等证据。
- 写次日目标和阻塞；阻塞必须关联风险 ID 或外部依赖。
- 成员 4 检查所有新增 PR 是否完成风险判断。

### 阶段最后一天

正式验收日为 07-27、08-03、08-10、08-17：

1. 作者按任务卡逐项演示。
2. 非作者复现关键测试或操作。
3. 风险表同步状态、证据和下周动作。
4. 项目负责人决定通过、有条件通过或不通过。
5. 未通过任务不得静默平移，必须写明影响和新截止日。

## 7. 本地与 CI 门禁

Windows：

```powershell
.\scripts\quality-check.ps1
```

macOS/Linux：

```bash
bash scripts/quality-check.sh
```

除统一门禁外，任务必须运行与改动相称的定向测试。支付/库存需要重复与并发测试；migration 需要 upgrade/downgrade；部署与备份需要真实恢复/回滚演练。

## 8. 评审拒绝条件

出现任一情况，评审人应退回 PR：

- 没有任务 ID、解决方案、修改范围或验收人。
- 关联风险未更新，或用 `R-none` 回避明显风险。
- 把规划、mock、脚本运行成功写成生产能力完成。
- 行为变化没有测试，migration 没有回滚说明。
- 未经协商修改其他成员主责范围。
- 包含密钥、用户数据、未知授权资产或生产数据库文件。
- P0 未关闭却要求发布或接受真实款项。

## 9. 完成定义

任务只有在代码/数据/文档产物、自动化门禁、定向验证、风险更新、回滚说明和非作者验收全部具备时才算完成。合并 PR 不等于业务验收完成；任务卡状态只能在验收证据生成后改为 `已完成`。
