# 胖虫项目整体优化计划

## 1. 项目现状概览

本项目包含根目录下的资料与脚本，以及 `ecommerce` 电商子项目。当前主要技术栈为：

- 前端：Vue 3、Vite、Pinia、Vue Router、TailwindCSS、Axios。
- 后端：FastAPI、SQLAlchemy Async、Pydantic、PostgreSQL、Redis、Alembic。
- 部署：Docker Compose、Nginx、前后端分离。
- 数据：`database/init.sql`、`database/seed.sql`、后端模型与 Alembic migration 并存。

当前验证基线：

- 前端生产构建可通过。
- 后端现有测试可通过，共 25 个用例。
- 后端存在 Pydantic v2 `class Config` 弃用警告，需要纳入中期技术债处理。

当前主要风险：

- 多个前端源码与文档中的中文、符号读取结果出现乱码，可能影响实际文案维护、搜索、SEO 与长期协作。
- 前端已经有黑绿电竞基础，但商品主视觉不足，部分页面依赖 emoji 或占位视觉，品牌质感还没有达到高端硬件官网的完成度。
- 后端 API 路由承载了较多业务逻辑，后续订单、支付、库存、后台管理扩展时维护成本会升高。
- 数据库 schema 已覆盖核心电商实体，但审计、状态历史、支付流水、库存流水等生产级能力仍不完整。
- Docker Compose 开发与生产边界不够清晰，生产环境需要避免源码挂载、默认弱密钥和 `DEBUG=true`。

本计划的前端风格参考 [Razer 官网](https://www.razer.com/) 的设计气质：深黑背景、高对比电光绿、强产品图、硬核性能表达、清晰购买转化。该参考仅用于设计语言借鉴，不使用 Razer 商标、素材或文案。

## 2. Razer 风格前端升级方案

### P0：先保证视觉与文案可信

- 全量检查 `frontend/src`、根目录 `README.md`、`ecommerce/README.md` 与现有 docs 的编码，统一为 UTF-8，修复乱码文案、损坏字符串和异常符号。
- 移除页面中作为商品、分类、功能图标的 emoji 占位，替换为真实商品图、品牌自有图标或简洁的 lucide/iconfont 图标。
- 建立统一设计 token，继续使用 Tailwind，不引入 React、Next.js、Nuxt 或新的 UI 框架。
- 统一基础视觉：
  - 主色：`#44D62C`，用于重点 CTA、选中态、价格、焦点环和少量高亮线条。
  - 背景：接近纯黑的深色体系，避免大面积蓝灰感。
  - 文本：白色标题、浅灰正文、中灰辅助信息，确保暗色可读性。
  - 圆角：按钮、输入框、卡片以 8px 为主，减少过圆的移动端卡片感。
  - 阴影：优先使用边框、光线和 hover 高亮，不使用过多漂浮卡片。

### P1：首页与商品页改造

- 首页首屏改为产品优先的沉浸式 hero：
  - 使用真实主机、笔记本、DIY 装机图或自有渲染图作为第一视觉。
  - H1 聚焦胖虫品牌与核心产品能力，例如 DIY 高性能整机、蓝天准系统、专业调校。
  - CTA 保持两个以内：查看产品、开始定制。
  - 首屏底部露出下一段商品/系列内容，避免纯海报式落地页。
- 商品列表页改为高密度暗色电商界面：
  - 左侧分类筛选、顶部排序与搜索保持稳定布局。
  - 商品卡突出图片、型号、核心配置、价格、库存/销量、加入购物车。
  - hover 使用边框、电光绿细线和轻微位移，动效控制在 150-250ms。
- 商品详情页强化转化：
  - 左侧产品图/图库，右侧价格、规格、库存、购买动作。
  - 下方分区展示配置参数、性能亮点、散热/质保/售后。
  - 对 DIY 配置商品展示兼容性、功耗、预算与推荐等级。
- DIY 装机页从“表单堆叠”升级为配置工作台：
  - 左侧配件类别，中央配件选择，右侧实时价格、功耗、兼容性与提交按钮。
  - 不把核心工作台放进装饰性卡片中，保持工具界面扫描效率。

### P2：动效与品牌细节

- 使用克制的硬件感动效：导航吸顶模糊、CTA 发光边框、商品图轻微缩放、配置步骤状态变化。
- 避免大面积渐变、装饰光球、纯氛围背景；视觉资产应能直接识别产品、配件或装机状态。
- 为移动端建立独立节奏：首屏图片可裁切但不能遮挡商品主体，按钮和价格区域保持一屏内可操作。

## 3. 前端工程与体验优化

### P0：质量基线

- 保留现有 Vue 3、Vite、Pinia、Vue Router、TailwindCSS 技术栈。
- 修复乱码文案后，为关键页面增加基础快照或组件测试：
  - 导航、商品卡、购物车数量、登录态菜单。
  - 商品列表加载、空状态、接口错误状态。
  - 购物车本地 session 与登录态合并前后的展示。
- 将 `alert()` 类交互统一替换为现有 `Toast.vue` 或统一通知组件。
- 所有图片补齐 `alt`，商品图设置固定比例、懒加载、占位背景和错误兜底。

### P1：状态与 API 调用

- 保持 `src/api/index.js` 作为 API 聚合入口，但拆分领域模块：
  - `auth`
  - `products`
  - `cart`
  - `orders`
  - `payment`
  - `admin`
- 统一接口错误模型，前端只消费 `displayMessage`、`code`、`fieldErrors` 等稳定字段。
- 购物车 store 中区分三类状态：
  - 后端购物车。
  - 匿名 session 购物车。
  - 本地降级缓存。
- 对结算、下单、支付状态查询加入加载中、失败重试、重复提交保护。

### P2：性能与可维护性

- 商品图片使用 WebP/AVIF，按卡片、详情页、hero 三种尺寸输出。
- 路由级代码拆分已具备，继续控制首屏 bundle：第三方库按需引入，避免把后台页面逻辑带入前台首屏。
- 补充 ESLint/Prettier 或等价格式化约束，保证 Vue、JS、TS 文件风格稳定。
- 建立视觉回归检查清单：桌面、平板、手机三档截图验证导航、首屏、商品卡、购物车与 DIY 页面。

## 4. 后端架构优化

### P0：生产安全与一致性

- 修复 Pydantic v2 弃用写法，将 schema 与 settings 中的 `class Config` 迁移到 `ConfigDict`。
- 统一错误响应结构：
  - `code`：稳定业务错误码。
  - `message`：用户可读错误。
  - `detail`：调试或字段级信息。
  - `request_id`：方便日志追踪。
- 为所有写操作加入一致的权限、参数校验和审计记录。
- 检查 CORS、SECRET_KEY、支付配置、Redis 密码和数据库密码，禁止生产默认值。

### P1：API/service 分层

- 将路由文件中的业务逻辑逐步迁移到 service 层：
  - `ProductService`：商品查询、筛选、上下架、库存读取。
  - `CartService`：匿名购物车、登录购物车、合并、数量校验。
  - `OrderService`：下单、取消、发货、状态流转。
  - `PaymentService`：支付创建、回调验签、幂等处理。
  - `AdminService`：仪表盘聚合查询、后台筛选。
- API 层只负责依赖注入、请求 schema、响应 schema 与 HTTP 状态码。
- 统一分页响应结构，避免前台和后台接口各自返回不同字段。
- 订单状态流转集中定义，禁止路由中散落字符串判断。

### P1：订单、库存与支付可靠性

- 下单继续使用数据库事务和 `SELECT FOR UPDATE` 控制库存并发。
- 支付回调必须幂等：
  - 以第三方支付流水号、订单号、回调事件 ID 建唯一约束。
  - 已处理回调直接返回成功，不重复改订单状态。
  - 回调金额、订单状态、支付渠道、签名必须全部校验。
- 取消订单、支付超时、退款、发货等动作写入状态历史。
- 购物车合并要由后端校验 session 归属，不能只依赖前端传入 session ID。

### P2：后台与扩展能力

- 管理后台 dashboard 聚合查询可以改为专用统计 service，并按日、订单状态、热销商品缓存短时间结果。
- 第三方物流、邮件通知、支付服务使用适配器接口，避免业务代码绑定单一供应商。
- 增加 request id、结构化日志、慢接口日志和异常追踪。

## 5. 数据库与数据模型优化

### P0：schema 与 migration 职责

- 明确职责边界：
  - `database/init.sql`：仅用于全新环境初始化。
  - `database/seed.sql`：仅用于演示和开发数据。
  - Alembic migration：生产 schema 演进唯一来源。
- 禁止在生产启动时依赖 `Base.metadata.create_all()` 自动补 schema，生产环境必须走 migration。
- 为现有 schema 生成一次完整基线检查，保证 SQL 文件、SQLAlchemy model、Alembic migration 三者一致。

### P1：索引与查询优化

- 商品列表建议索引：
  - `(is_active, category_id, created_at DESC)`
  - `(is_active, is_featured, sold_count DESC)`
  - `(is_active, price)`
  - `slug` 继续唯一索引。
- 商品搜索建议：
  - 短期继续 `ILIKE`，同时限制关键词长度和分页上限。
  - 中期引入 PostgreSQL `pg_trgm` 或更完整的中文搜索方案。
  - 对 `name`、`brand`、`model` 建组合搜索策略，不只依赖单字段 `to_tsvector('simple', name)`。
- 订单后台建议索引：
  - `(status, created_at DESC)`
  - `(user_id, created_at DESC)`
  - `order_no` 唯一索引保持。
- 用户后台建议索引：
  - `email`、`phone`、`username` 已有索引，后台模糊搜索可评估 trigram。

### P1：生产级业务表

- 新增库存流水表：
  - 记录下单扣减、取消返还、后台调整、售后返还。
  - 字段包含 `product_id`、变化数量、变化前后库存、原因、关联订单、操作人。
- 新增支付流水表：
  - 记录支付请求、第三方交易号、金额、状态、回调原文摘要、验签结果。
  - 对第三方交易号和回调事件建立唯一约束。
- 新增订单状态历史表：
  - 记录订单从 pending 到 paid、shipped、completed、cancelled、refunded 的每次变化。
  - 字段包含旧状态、新状态、原因、操作人、创建时间。
- `audit_logs` 继续保留，用于管理员操作审计，不替代业务流水。

### P2：JSONB 使用边界

- `products.specs` 适合保存展示型参数，如 CPU、GPU、内存、硬盘、屏幕、功耗。
- 高频筛选字段不要只放在 JSONB 中，应同步为结构化列或建立专门规格表。
- `products.images` 可保存多图数组，但需要规范字段：url、alt、sort_order、type。
- 如果未来 DIY 兼容性规则复杂，应独立出配件、插槽、功耗、兼容性规则表，而不是把规则塞进 JSONB。

## 6. 安全、性能、部署与监控优化

### P0：部署安全

- Docker Compose 区分开发与生产：
  - 开发：允许源码挂载、热更新、`DEBUG=true`。
  - 生产：使用构建产物镜像，不挂载源码，`DEBUG=false`，强制设置密钥。
- `.env` 必须提供强密码和强 `SECRET_KEY`，启动脚本检查默认值并拒绝生产启动。
- Nginx 生产配置开启 HTTPS、HSTS、gzip/brotli、静态资源长期缓存和 API 反向代理超时限制。
- 上传目录限制文件类型、大小、扩展名和 MIME，并考虑对象存储或独立静态资源服务。

### P1：缓存与性能

- Redis 优先用于：
  - 热门商品列表短缓存。
  - 分类列表缓存。
  - 首页推荐商品缓存。
  - 支付/验证码/临时 session 等短生命周期数据。
- 不缓存强一致库存判断，下单仍以数据库锁和事务为准。
- 后端增加慢查询日志，记录接口名、耗时、SQL 关键上下文和 request id。
- 前端静态资源通过 Nginx 设置指纹缓存，图片走 CDN 或独立静态域名。

### P2：监控与告警

- 健康检查分层：
  - `/health`：应用进程健康。
  - `/ready`：数据库、Redis、关键配置可用。
- 日志结构化输出 JSON，至少包含时间、级别、request_id、path、status、duration、user_id。
- 关键业务指标：
  - 下单成功率。
  - 支付成功率。
  - 库存不足次数。
  - API P95/P99 响应时间。
  - 前端 JS 错误率。
- 接入错误追踪工具或自建异常日志聚合，避免只依赖容器日志排查。

## 7. 分阶段实施路线图

### 第一阶段：P0 基线修复

目标：让项目文案、构建、安全配置和核心链路可信。

- 修复中文编码、乱码文案和明显损坏模板。
- 保持前端构建与后端测试通过。
- 统一前端基础色彩、字体、按钮、输入框、卡片和通知组件。
- 检查生产默认配置，禁止弱密钥、默认密码和 `DEBUG=true` 进入生产。
- 修复 Pydantic v2 弃用警告。

验收：

- 首页、商品列表、商品详情、购物车、登录注册、后台入口中文显示正常。
- `npm run build` 通过。
- `python -m pytest -q` 通过，且 Pydantic 弃用警告明显减少或消除。
- 生产 `.env` 缺少关键密钥时应用拒绝启动或明确报错。

### 第二阶段：P1 体验与架构升级

目标：完成 Razer 气质的前台主体验，并降低后端维护成本。

- 重做首页首屏、商品卡、商品详情页与 DIY 工作台视觉。
- 补齐真实商品图、图片规格、懒加载和错误兜底。
- 拆分前端 API 模块，统一错误与分页处理。
- 后端引入 service 层，优先迁移购物车、订单、支付、商品查询。
- 增加组合索引、库存流水、支付流水、订单状态历史。

验收：

- 前台核心购买链路在桌面和移动端都可顺畅完成。
- 商品列表筛选、搜索、排序和分页响应稳定。
- service 层覆盖订单、购物车、支付的关键业务逻辑。
- 订单、支付、库存变化均可追踪。

### 第三阶段：P2 性能、监控与运营能力

目标：让项目具备持续上线和运营迭代能力。

- 增加 Redis 缓存策略和失效规则。
- 引入慢查询、结构化日志、错误追踪和基础监控。
- 完善后台统计、订单筛选、商品运营能力。
- 建立视觉回归、API 集成测试、迁移测试和部署检查清单。

验收：

- 首页和商品列表首屏加载稳定，关键 API 有耗时指标。
- 管理后台可快速定位订单、用户、商品和支付问题。
- 新增 migration 可在测试数据库中自动验证。
- 线上异常可以通过 request id 追踪到日志和具体接口。

## 8. 验收标准

本优化计划执行完成后，应满足以下标准：

- 设计层面：胖虫保留自有品牌，形成黑底、电光绿、高性能硬件主视觉的统一风格；不使用 Razer 商标、素材或文案。
- 前端层面：核心页面文案无乱码，商品图真实可信，组件状态完整，桌面与移动端布局不重叠、不溢出。
- 后端层面：路由层变薄，业务规则集中在 service，错误、分页、状态流转和权限校验一致。
- 数据库层面：高频查询有索引支撑，订单、支付、库存、审计可追踪，migration 是生产 schema 演进来源。
- 安全层面：生产配置无默认弱密钥，支付回调幂等，上传、CORS、认证、权限和日志满足基础上线要求。
- 性能层面：图片与静态资源可缓存，热门读接口可短缓存，下单库存一致性不依赖缓存。
- 质量层面：前端构建、后端测试、API 集成测试、数据库迁移测试纳入每次发布检查。

## 9. 后续执行建议

建议先以一个小版本完成 P0，再进入视觉大改。原因是当前最大的不确定性不是配色，而是文案编码、模板可信度、生产配置与后端技术债。P0 完成后，再推进首页、商品页和 DIY 工作台的视觉升级，会更稳也更容易验收。

推荐首个实施包：

- 修复编码与乱码文案。
- 建立 Tailwind 设计 token 和基础组件规则。
- 重做首页首屏和商品卡。
- 修复 Pydantic v2 弃用警告。
- 增加商品列表、购物车、订单的组合索引迁移。
- 区分 Docker Compose 开发与生产配置。
