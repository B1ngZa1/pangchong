## 4. 两个最高优先级风险组

### 🔴 Critical 1：交易金额与支付链路不能信任

1. **DIY 定制商品价格由客户端提交，后端直接采信。** `CustomOrderItemCreate.price` 是请求字段，创建订单时直接用它累计总价：`ecommerce/backend/app/schemas/order.py:22-36`、`ecommerce/backend/app/api/orders.py:134-148`。攻击者可以绕过前端，将高价配置改成极低价格后下单。`[仓库证据]`
2. **正式支付宝支付未实现。** 生产分支只拼接查询参数；SDK 调用和 RSA2 签名代码均被注释，生产回调验签固定失败：`ecommerce/backend/app/api/payment.py:42-78`、`80-107`。微信支付明确返回 501：`ecommerce/backend/app/api/payment.py:173-180`。`[仓库证据]`
3. 支付没有独立支付流水表、回调事件唯一约束、第三方交易号唯一约束和订单状态历史；并发回调只靠读取 `order.is_paid`，不是数据库级幂等。`[仓库证据]` `[推断]`

**上线门槛：** DIY 请求只提交配置 ID/版本，后端从可信商品表重新定价；完成真实支付 SDK、签名/验签、金额与商户校验、事件幂等、支付流水、超时关单和退款闭环，并用真实沙箱端到端验证。`[推断]`

### 🔴 Critical 2：生产配置存在可直接利用的暴露面

1. `docker-compose.prod.yml` 在新数据库初始化时挂载 `seed.sql`；该脚本写入公开密码 `test123456` 的管理员 `admin`：`ecommerce/docker-compose.prod.yml:13-17`、`ecommerce/database/seed.sql:158-166`。按现有生产 Compose 首次启动会创建已知管理员账户。`[仓库证据]`
2. Compose 暴露 443 并挂载证书目录，但 Nginx 仅 `listen 80`，没有 TLS server block、证书或 HTTP→HTTPS 跳转：`ecommerce/docker-compose.prod.yml:76-86`、`ecommerce/docker/nginx/nginx.conf:47-110`。`[仓库证据]`
3. 后端镜像以 root 运行，启动命令仍带 `--reload`，没有 worker/资源限制/只读文件系统：`ecommerce/backend/Dockerfile:1-31`。`[仓库证据]`
4. 依赖基线未通过：`npm audit --omit=dev` 报告 1 个高危生产依赖问题；`pip-audit` 报告 7 个包共 27 条已知漏洞记录，其中涉及 FastAPI、python-multipart、python-jose、Starlette 和 aiosmtplib。部分记录是同一漏洞的重复别名，且 pytest 属于开发依赖，但当前基线仍不适合上线。`[工具验证]`

**上线门槛：** 生产初始化不导入测试用户/订单；默认密钥或沙箱开关存在时拒绝启动；升级依赖并复测；配置真实 TLS；应用以非 root、非 reload、多 worker 模式运行；对登录、注册、支付、上传和找回密码增加限流与告警。`[推断]`

- 没有仓库内 CI 工作流，也没有自动执行迁移、依赖审计、构建、测试和镜像扫描的发布门禁。`[仓库证据]`

### 🟠 可靠性与运维

- `/health` 只根据数据库 URL 判断“local/external”，没有真正探测数据库、Redis、存储和支付依赖；可能在依赖失效时仍返回 healthy：`ecommerce/backend/app/main.py:122-135`。`[仓库证据]`
- 未发现结构化应用日志、请求 ID、Sentry/同类错误追踪、Prometheus 指标、支付成功率/下单成功率告警。Nginx 只有基础访问日志。`[仓库证据]`

- 本次 Docker 引擎未运行，因此只验证了 Compose 语法，未验证四个容器的冷启动、健康状态、迁移和反向代理。`[工具限制]`

## 6. 中国大陆上线合规边界

本节按“公司主体、自营电脑及配件、站内收款、中国大陆服务器”假设评估，不构成正式法律意见。若允许第三方商户入驻或提供交易撮合，许可范围会显著扩大，应由律师与云服务商确认是否涉及增值电信业务许可。`[推断]`

- 工信部现行规则要求境内非经营性互联网信息服务履行备案，材料齐全后省通信管理局应在 **20 个工作日内**办理；备案号需在首页底部展示并链接备案系统。[工信部《非经营性互联网信息服务备案管理办法》](https://www.miit.gov.cn/gyhxxhb/jgsj/cyzcyfgs/bmgz/xxtxl/art/2024/art_84a0cfa0ebd049bbbe751dca9a008e56.html) `[外部依据]`

## 7. 8–12 周商业 MVP 路线图

以下排期假设五人团队中至少有 3 个全职当量：1 名前端/全栈、1 名后端、1 名测试/运维；产品、法务、财务和运营能及时确认规则。`[推断]`

### 第 0–2 周：堵住资金与管理员风险

- 服务端重建 DIY 配置与价格，拒绝客户端价格；全程使用 Decimal/分为单位。
- 生产环境移除 seed，创建一次性管理员引导流程；默认密钥、`ALIPAY_SANDBOX=true`、空支付密钥时拒绝生产启动。
- 升级前后端漏洞依赖，执行 SCA、镜像扫描和回归测试。
- 登录/注册/支付/上传限流；增加受信 Host、请求 ID、审计日志和安全告警。
- 明确首发 SKU、真实库存来源、价格更新责任人。

**退出条件：** 无 P0 漏洞；任何客户端改价均无法改变订单金额；生产初始化没有已知账户。`[推断]`

### 第 2–5 周：打通真实交易闭环

- 接入一个正式支付渠道；实现签名、验签、金额/商户校验、幂等、超时关单、退款和对账。
- 建立 payment、inventory_ledger、order_status_history、refund/after_sale 表及后台页面。
- 接入真实物流，第三方失败时展示“暂不可用”，禁止返回模拟签收。
- 增加发票申请最小流程与可追溯客服/售后入口。
- 用 PostgreSQL/Redis 做 API 集成测试，覆盖并发下单、重复回调、退款、取消和发货。

**退出条件：** 沙箱真实端到端连续通过；重复回调不重复入账；订单、支付、库存可对账。`[推断]`

### 第 4–7 周：建立可恢复的生产环境

- 完成域名、TLS、HTTP→HTTPS、非 root 镜像、多 worker、资源限制和生产反向代理。
- 建立 CI/CD：测试、类型检查、依赖/镜像扫描、migration dry-run、部署、健康检查和自动回滚。
- 配置结构化日志、错误追踪、核心指标、支付/下单/5xx 告警。
- 建立数据库与资产备份，至少执行一次“从空环境恢复”的计时演练。
- 建立 staging，与 production 使用同构配置和独立凭据。

**退出条件：** 可在目标 RTO 内恢复；发布失败可回滚；关键依赖失效会告警而非静默。`[推断]`

### 第 5–8 周：合规、内容和运营验收

- ICP、公安联网备案、营业执照公示、支付商户和开票材料并行推进。
- 法务复核隐私政策、用户协议、销售/保修/退换规则；实现同意留痕、注销与数据请求流程。
- 完成首发 SKU 图片/模型授权、规格、价格、库存和售后承诺抽检。
- 编写客服、退款、物流异常、数据泄露和支付故障 runbook。

**退出条件：** 证照/备案与页面公示符合实际业务；客服可按演练处理异常订单。`[推断]`

### 第 8–12 周：灰度付费试运营

- 先放 10–20 名真实用户或每日限量订单，人工逐单对账。
- 做一次基础渗透测试、峰值 2–3 倍压测、移动端弱网和主流浏览器验收。
- 连续 7–14 天观察支付成功率、下单失败率、5xx、库存差异、退款时长和客服工单。

**退出条件：** 无阻断级缺陷、账实一致、备份可恢复、告警可用，再逐步放量。`[推断]`
